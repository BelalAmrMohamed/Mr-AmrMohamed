# Admin Dashboard — Setup

A private dashboard for Mr. Amr at `/admin` showing live visitor count,
traffic over time, top pages/referrers/countries/devices, AI assistant
usage, and contact-link clicks. Nobody can reach it without signing in with
an authorized account — it isn't linked from the public site anywhere.

Sign-in supports **both** "Continue with Google" and email/password, both
handled entirely by Supabase Auth. **There is no password of ours anywhere
in this system** — not for Google, and not for email/password either:
Supabase stores and manages those credentials itself. When Mr. Amr changes
his Google password, or resets an email/password login, nothing here needs
to change. Access is controlled purely by an email allowlist in the
database.

## 1. Push the database migrations

```bash
supabase db push
```

This applies, in order:

- `20261009000000_admin_analytics.sql` — the original schema (already
  applied to production; **do not edit this file**, Supabase has no way to
  "re-push" a changed migration against a database that already ran it).
  Creates `page_views`, `visitor_heartbeats`, `ai_chat_events`,
  `contact_clicks`, plus the (now superseded) `admin_users`/`admin_sessions`
  tables from the original password-based design.
- `20261009103000_admin_analytics_auth_update.sql` — the follow-up
  migration that creates `admin_emails` (the allowlist, pre-seeded with
  both your emails) and drops the old `admin_users`/`admin_sessions`
  tables, since Supabase Auth replaces them entirely.

**If you ever need to change the schema again, always add a new migration
file with a later timestamp — never edit one that's already been pushed.**

RLS is on for every table with **no public policies** — only the
service-role key (used server-side only) can read or write any of it.

## 2. Environment variables

You already have the three that matter here, in both `.env.local` and
Vercel:

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
SUPABASE_SERVICE_ROLE_KEY
```

The first two are also used by the admin pages directly (via
`/api/public-config`, since this project has no build step to inject env
vars into static HTML) — **if either is missing or misnamed, sign-in fails
with a 500 from `/api/public-config`**, and the dashboard/sign-in page will
now show you exactly which variable is missing. If you see that error:
double-check the names match exactly (`NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`) in `.env.local`, and **restart your
local dev server** after editing `.env.local` — it's only read on startup.

Also set, for the scheduled cleanup job (optional but recommended):

```
CRON_SECRET=generate_a_long_random_string
```

## 3. Enable sign-in providers in Supabase

**Google** — you've already created the OAuth client in Google Cloud
Console and connected it to Supabase. Confirm:

1. **Supabase → Authentication → Sign In / Providers → Google** is
   **Enabled**, with your Client ID and Secret filled in.
2. **Supabase → Authentication → URL Configuration → Redirect URLs**
   includes your site's admin URL (you've already added
   `https://mr-amr-mohamed.vercel.app/` and `http://localhost:3000/`,
   which cover the admin pages too since they're on the same origin).

**Email** — already **Enabled** by default in Supabase (confirmed in your
screenshot). Nothing to configure here.

## 4. Create the sign-in accounts

Google needs no extra step — anyone with an allowed Google account (see
step 5) can just click "Continue with Google."

For **email/password**, create the accounts directly in Supabase, since
that's now the single source of truth for credentials:

1. Supabase → **Authentication → Users → Add user → Create new user**
2. Enter the email (must match an entry in `admin_emails`, see step 5) and
   a password, and check **Auto Confirm User** so no email verification
   step is required.
3. Repeat for each person who should be able to use email/password.

Mr. Amr (or you) can change this password anytime from the same Users page
— no code, no redeploy, no env vars.

## 5. Who can sign in

Controlled entirely by the `admin_emails` table — already seeded with:

| email | label |
|---|---|
| `belalamrofficial@gmail.com` | Belal (testing) |
| `amrmohammed4111@gmail.com` | Mr. Amr |

This applies to **both** sign-in methods — an email must be on this list
to get into the dashboard, whether they signed in with Google or with a
Supabase email/password account.

To add or remove someone later, open Supabase → Table Editor →
`admin_emails` and insert/delete a row. No redeploy, no env var changes,
nothing on Vercel. (Or via SQL: `insert into admin_emails (email, label)
values ('someone@gmail.com', 'Label');`)

Anyone who signs in (either method) but isn't on this list gets a clear
"not authorized" message and is signed back out automatically.

## 6. Sign in

Visit `/admin` and either click **Continue with Google** or use the
email/password form below it. If the account's email is on the allowlist,
you land on `/admin/dashboard.html`, which refreshes itself every 15
seconds.

## How it works, briefly

- The sign-in page and dashboard load the Supabase JS client from a CDN and
  talk to Supabase Auth directly — for Google OAuth and for
  `signInWithPassword`. No session cookie of our own, no password table of
  our own.
- Every `/api/admin/*` call sends the Supabase access token as
  `Authorization: Bearer <token>`. The server asks Supabase who that token
  belongs to (regardless of which method they signed in with), then checks
  the email against `admin_emails`.
- `public/js/analytics.js` runs on every public page: it sends a
  `pageview` beacon on load and a `heartbeat` every 20s while the tab is
  visible/open. No cookies, no PII — just a random ID kept in
  `localStorage` so repeat visits can be counted as the same visitor.
- "Live now" on the dashboard = heartbeats received in the last 60 seconds.
- The AI chat widget (`public/ai/app.js`) reports anonymous usage events
  (chat started, message sent, tool used, quiz completed/score) — never
  the actual conversation text.
- `api/admin/cleanup.js` is wired to a Vercel Cron (`vercel.json`, every 6h)
  to clear stale heartbeats so the table stays small.

## Troubleshooting

**"Missing environment variable(s): ..." / 500 from `/api/public-config`,
or "Server is missing NEXT_PUBLIC_SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY"
from `/api/admin/me`**

First, visit `/api/admin/diag` (locally: `http://localhost:3000/api/admin/diag`)
— it reports exactly which required env vars the *running* serverless
process can see (never their values, just true/false), which is more
reliable than re-reading `.env.local` by eye.

If `.env.local` has the right names and values and the dev server has been
restarted but `diag` still shows `false`, check **Vercel → Project Settings
→ Environment Variables → (the var) → Environments**. `vercel dev` pulls
Vercel's own **Development** environment when the project is linked (a
`.vercel/` folder exists) — if a variable is scoped only to
**Production**, `vercel dev` won't see it, even though `.env.local` has it
and even though it works fine once actually deployed to production. Edit
the variable and check **Development** (and **Preview**, for preview
deployments) alongside Production, then restart `vercel dev`.

**"X is not authorized to view this dashboard"**
Their email isn't in `admin_emails` yet — add it there (step 5).

**Email sign-in says "Incorrect email or password"**
The account doesn't exist yet in Supabase Auth, or the password is wrong —
create/reset it from Supabase → Authentication → Users (step 4).
